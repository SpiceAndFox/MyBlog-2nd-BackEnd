# Memory 业务拒绝与动态纠错

日期：2026-09-10。本文件仅记录实现，不由运行时代码或测试加载。

该报告记录 Todo force drain 失败，外层原因为 `semantic_schema_invalid`，失败任务为 `64809c5d-2246-4e3f-bddd-a823874851c6`；当时 schema 重试上限为 2。
报告保留当时的失败状态，代码修复不意味着 cutover 已完成。

## Reducer 的处理边界

`modules/memory/domain/todoRevision.js` 比较编译后实际生效的 text、actor、requester 和 dueAt；日期按同一时刻比较，文本不做模糊语义判断。

| 候选与当前条目的差异 | 处理 |
| --- | --- |
| 业务字段和来源都相同 | 记录 `decision=noop`、`noopReason=unchanged_todo`；不更新条目元数据，任务游标和 revision 正常推进 |
| 只有来源不同 | 按既有语义替换来源、更新条目的消息边界；保留状态、原期限及 becameOverdueAt |
| 业务字段有变化 | 沿用真实修改规则；逾期待办必须有得到证据支持且晚于 task.now 的新期限，恢复时不能同时更换 actor/requester |

来源、可写目标、字段类型、文本长度、来源上限和同任务冲突检查仍然执行。相同期限不能掩盖实际的文本或参与者修改；没有将任意 revise 自动改成 noop。来源更新不自动并集，以免改变原有证据替换语义。

## 业务拒绝后的重试

Reducer 预检错误定位到具体 change 和字段。Provider Adapter 保留经过解析的原始 wire 输出，重试向模型回传原始 v2 候选及映射后的 v2 字段路径。生产调用不再把内部 Semantic IR 当作模型刚才的回答。注入式适配器缺少原始候选时，仅对合法 IR 做明确标记的重新编码。

错误日志及持久化反馈标记 `validationLayer=business`，保留候选的协议、schema hash 和原始结构校验结果；拒绝记录另存 `outputKind`，区分原始 wire、重新编码与 Profile 的 `specialist_bundle`。错误反馈使用 repair policy v10，持久化恢复后仍可生成相同修复消息。

专用反馈覆盖逾期改期冲突、逾期恢复时更换参与者、来源超限、与已有条目重复，以及同一目标的操作冲突。常规 prompt 和受保护的 JSON 示例未修改。

## 扩展与组合错误

- 领域校验通过 `writeIssue` / `rejectWriteIssues` 提供稳定原因、字段位置及必要约束。没有专用模板的新业务规则使用 `BUSINESS_RULE_VIOLATION`；开发者提供 `constraint` 后即可得到通用提示，无须新增一套重试流程。反馈元数据仍受白名单和长度限制，不能传递任意条目或原始消息。
- 专用错误的描述、修复指令和提示统一注册在 `renderBusinessRepair.js`，避免修复计划和实际提示各维护一份错误分支。
- 普通归约一次收集最多 8 条错误。同一 Todo 的长度、来源、日期和参与者约束可同时报告；不同目标继续独立检查。同一目标的后续操作报告 `CHANGE_TARGET_CONFLICT`，并指出第一条冲突 change。错误位置及关联位置同时映射回 wire。
- 每个目标的写入守卫在修改前执行；成功预检只影响私有副本。任何错误都会拒绝整个候选，不提交部分状态、事件或游标。维护模式沿用既有处理方式。
- 来源上限检查的是展开及合并后的底层证据数，提示不再将它等同于模型的 `sources` 数组长度。
- Profile 的候选保存和复用与错误类型解耦：业务拒绝、wire schema、语义契约、JSON 解析或输出缺失均保存完整子任务 bundle，其中包括各自的候选、协议元数据和待修复反馈。多个子任务同时失败时，各自保留对应反馈；修复成功才清除该子任务的错误，避免把结构合法但业务仍失败的候选视为可复用结果。
- Profile 恢复先检查任务及输入指纹，再按当前绑定 schema 和语义契约重新校验保存结果，仅对待修复子任务发送其自己的候选和局部错误索引。指纹忽略 JSON 对象字段顺序，保留数组顺序。其他仍合法的结果直接复用，输入变化或保存结果失效时重新生成。合并结果仍需通过业务预检后原子提交，调用数和 token 只统计实际 Provider 请求。
- 新 bundle 的重启恢复不依赖进程内缓存。旧业务 bundle 无指纹和子任务反馈时仍可读取，按原有局部错误标记和绑定校验决定复用；历史结构错误若只保存了失败子任务输出，则无法恢复当时未持久化的其他结果。
- 拒绝候选不可用或超出持久化大小限制时，只使用反馈，不将旧候选配到新错误上。

本次没有增加重试预算，也不承诺任意新业务错误均可自动修复。诊断数量有界；编译或来源失败仍走原有恢复流程。

例如集成测试里的候选将一个截止于 2026-01-03 的逾期待办改为 2026-01-04，但任务时间已经是 2026-09-10。动态反馈指出：

- 出错位置 `$.results.todos.changes[0].due`，目标 `T1`。
- 原始、候选解析后的 UTC 截止时刻，以及本次状态判断时间。
- 核对日期模式、数值与来源锚点；不能虚构未来日期，也不能用当前时间重新解释历史消息。
- 若只补证据，业务字段保持原值、due 使用 `{"mode":"keep"}`；有实际业务修改时不能用 keep 掩盖。
- 无法合法裁决时使用 `unable_to_decide`；仅在确实无变化时使用 `noop`。

这些反馈按已知错误生成修复方向，不替模型推断原始消息中不存在的事实，也不保证模型每次都能修复成功。
