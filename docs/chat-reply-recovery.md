# 未完成回复的恢复

后端接到发送或补回复请求后，即使浏览器断线，仍会继续生成并保存回复。重新打开会话可以读取已保存的结果。如果模型调用失败、用户主动停止或服务重启，最新未完成的一轮可以通过“补回复”恢复。

## 接口与约束

`POST /api/chat/sessions/:sessionId/messages/:messageId/resume`

- 使用正常登录鉴权；可传 `settings`，支持 JSON 和 SSE。消息内容和身份均从数据库读取，忽略客户端传来的替换内容。
- 只允许当前用户、当前会话中带有 turn/idempotency 身份的用户消息。已删除会话不能恢复。
- 未完成消息必须是该用户、该 preset 所有未删除会话中的最后一条消息。生成前和提交回复前均在 source write guard 保护下校验；已有后续对话时返回 `409 CHAT_RESUME_NOT_LATEST`。
- 已存在关联回复时返回原回复，不再调用模型。沿用发送队列和每个用户消息至多一条 assistant 的数据库唯一约束。
- 保留原消息内容、时间、turn 和请求标识；恢复后只追加关联回复。必要时将未完成消息绑定到当前记忆 generation，不触发 source mutation、删除或全量重建。
- 记忆覆盖不足时沿用等待机制，超时返回 `409 CHAT_MEMORY_COVERAGE_PENDING`。前端显示等待记忆恢复，恢复后可再次点击“补回复”。
- 消息列表提供 `reply_status`（`incomplete` / `complete`）和 `can_resume`；无 turn 身份的旧消息不自动推断为可恢复。
- SSE 必须收到 `done` 才视为保存成功；连接中断后重新读取消息确认是否已保存。已完成请求的 JSON 重放也能在流式模式正确显示。
- 点击“停止回复”会调用 `POST /api/chat/sessions/:sessionId/generations/:generationId/stop`。前端为每次发送、补回复和编辑后的重新生成分配独立的 `generationId`，停止操作按登录用户、会话和本次请求匹配。当前部署在同一个后端进程中协调生成和停止请求。

## 部署与使用

前后端均需更新；此变更不需要新增数据库迁移。后端重启、前端重新构建部署后，刷新网页，打开原来的历史会话，在最后一条未完成的用户消息下点击“补回复”。如果已经发送了后续消息，则在今天的会话中引用原问题继续。

本功能不会自动补发历史消息或批量调用模型。
