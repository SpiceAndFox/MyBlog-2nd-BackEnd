# 会话删改与记忆恢复

普通会话操作与隐私清除使用不同的执行路径：

- 移入回收站、恢复会话和编辑消息调用 `mutateSourceAndRebuild`，保留现有快照、事件和任务历史。
- 永久删除已经在回收站的会话（包括自动过期清理）只物理删除原始会话。有效记忆源没有变化，因此不递增 generation，不重置游标，不清理恢复历史；正在进行的重建仍按原进度继续。
- 删除整个 preset 等真正清除 scope 的操作仍使用原来的清理流程。旧版本已经提交的 privacy operation 继续兼容恢复。

## 安全恢复点

迁移 `016-source-history.sql` 新增 `chat_memory_source_history`。每次源变更与原始数据修改、记忆状态写入在同一事务中记录：generation、最早受影响的消息 ID、源是否未变、原因。

回滚可以搜索以前 generation 的快照，但必须有连续的变更记录，且候选快照的所有目标游标和来源引用均早于所有相关变更。来源内容哈希仍需逐一匹配。仅验证仍然保留的引用不够，因为旧记忆可能曾受后来已经遗忘的消息影响。

历史版本没有记录的 generation 不会被猜测为安全；记录缺口会停止跨代搜索。快照继续遵循已有 retention 配置，本改动不会延长为永久保留。

普通删改找不到安全快照、且需要从零处理的有效消息数超过一批 Librarian 消息（`CHAT_MEMORY_V2_LIBRARIAN_MESSAGE_BATCH_SIZE`）时，返回 HTTP 409 / `MEMORY_REBUILD_BASELINE_REQUIRED`。原始删改事务会回滚，避免在没有恢复点的情况下意外重放大量历史。显式全量重建仍保持原有行为。

## 聊天可用性

健康接口和发送前检查共用 `contextCoverage` 的近期原文窗口及 GapBridge 算法。结构合法不再等价于可以回复。

`memory.scope` 增加 `chatBlocked`、`availability`、`coverage` 和 `progress`。进度统计真实有效消息数，按最慢目标计算，不能用稀疏的全局消息 ID 比例代替。

前端展示阻塞原因和进度，保留普通更新的安静显示；阻塞时轮询健康状态，覆盖恢复后自动解锁。覆盖不足但用户消息已经提交时保留该消息，重试沿用同一个幂等键。编辑已经提交后，等待记忆期间不回显修改前的旧会话内容。

## 部署顺序

后端和同级 `BlogFrontEnd` 仓库都有改动，需要分别提交、推送和部署。

1. 停止应用工作进程并备份数据库。
2. 拉取后端代码，执行新增的 `migrations/memory/016-source-history.sql`（仅建表，可重复执行）。已有 `npm run migrate:memory-v2` 会包含它，但也会重跑其余历史迁移；按当前部署流程选择执行方式。
3. 更新并构建前端：`npm run build`。
4. 若已有记忆被清零，需要另行从已验证的备份恢复权威状态、新 anchor 和运行状态；本改动不会自动导入备份，也不会自动把旧 generation 当作恢复证明。
5. 验证恢复起点后再启动应用，检查后台推进及前端覆盖状态。

本次 Lina-Weil 的恢复应沿用已核查的 2026-09-24 备份，并在实际执行前重新验证现库。代码修复不等于生产数据已修复；拉取代码后，不要先启动旧的全量重放再进行恢复。
